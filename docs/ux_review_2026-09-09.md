## 从体验出发的架构建议

1. **先让状态明确，再优化耗时**。词库正在加载、失败、候选正在算、录音就绪是不同状态，应在 UI 中区别显示；首次载入 20 万词确实需要时间，但黑屏/没有反馈、加载完不自动补算是缺陷。
2. **输入事件与候选展示解耦**。候选属于可取消的计算，空格/标点/回车属于不可丢失的用户动作。现有 ImeRoot 同时维护二者，异步确认期间的新按键可能使确认结果失效。下一阶段宜抽出独立 InputSessionController，用有序事件处理提交动作，候选发布仍保留 latest-only。不要简单把解码放回主线程。
3. **统一引擎调度**。当前 Compose 自建单线程 dispatcher，而 Service 的 endSession / learning 开关直接操作同一个可变引擎。应统一到会话控制器，避免切换输入框与解码并发；控制器通过 PinyinEngine 接口工作。
4. **先测冷启动瓶颈再换引擎**。本轮加入无明文的 engine-ready 耗时，候选已有耗时日志；后续记录首帧、词库查询、Trie 构建、GC 和解码 P50/P95。若 Trie 初始化持续偏慢，再考虑构建工具预生成紧凑索引，避免每次冷启动重建大量对象。
5. **语音独立加载**。手机无系统 RecognitionService，系统识别无法工作；接入离线模型后，模型只在语音入口加载，闲置释放，与拼音初始化分开。准确率、内存和首次听写启动时间需真机评估。
6. **常用/最近内容由 Repository 持有**。页面只负责呈现，不用 rememberSaveable 替代持久化；符号丢失即是这种生命周期边界错误。
7. **构建成功不等于体验验收**。增加可重复的独立测试输入框/自动化用例，覆盖冷启动、连敲、换 App、候选尚未返回时按空格、权限拒绝和语音取消，不能仅凭能编译宣布完成。
